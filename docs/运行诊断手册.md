# 运行诊断手册（OPS Runbook）

> 目的：课程定时自动跑（run.yml schedule）**每天北京时间 00:00**（= UTC 16:00）触发。
> 若次日发现 run 异常，用本文快速定位→修复。每一条都来自线上真实踩坑，是可操作的 checklist。

---

## 0. 定时任务

- `run.yml` schedule：`0 16 * * *`（UTC 16:00 = 北京 00:00）。
- GitHub `schedule` 为**异步触发**，可能延迟数分钟，无 SLA，**不能**用于分钟级精确定时。
  若需要精确（如固定每隔 N 分钟），用本地/远程 cron 调 `gh workflow run run.yml -f action=scheduler`。

## 1. 看 run 结论的快速路径

```bash
# 最近一次 scheduler 运行结论
gh run list --workflow=run.yml --limit 5 --json databaseId,createdAt,event,status --jq '.[]|.[.databaseId|tostring] '

# 某个 run 的完整控制台（含 DIAG 行）
gh run view <run_id> --log | grep -E '\[scheduler\] (DIAG|TDVP: (next_task|queue has|frozen|reconcile))'

# 该 run 的产物里读 verdict
gh run download <run_id> -D ./art -n mvp-evidence-<run_id>
jq '{verdict, chapters_attempted, chapters_failed, chapters_timed_out, "checks":.evidence.checks, "runtime_result":.evidence.runtime_result}' art/**/evidence/result.json

# 当前课程状态（registry 快照，已随 run 提交到仓库）
git show origin/main:state/registry/265997861_151695658/tasks.json   # 解析出某章 status/consecutive_failures
```

## 2. 判定语义（做完即“真实完成”，不靠猜）

- 每章真正把视频播到 `ended_seen` 或 `isPassed=true` + `chapter_completed=true` 才算数。
- 冻结章（`BLOCKED` / consecutive_failures=max_attempts）**被 skip、不入队**，不是失败。
- `chapters_failed` 与 `chapters_timed_out` 为空 + `verdict=PASS` → 正常推进。

## 3. 常见失败模式 → 定位 → 修复（都实际发生过）

### 3.1 固定章节被反复重跑 / 永不跳过（曾经的死循环）
- **症状**：某章（如 121.157 点对点协议）每次 run 都在 `next_task=…` 出现，video 抓不到，`video_reload_count=3`，run FAIL。
- **根因（本次最终）**：`TASKS_DIR` 锚错到 `<repo>/app/state/registry`，运行时读不到含 BLOCKED 的 checkpoint
  → 冻结章在**输入端**就是 DISCOVERED → reconcile 冻结/章冻结/选前 gating 全部正确却不触发。
- **定位**：run 日志 `DIAG reconcile1 reg_entry=None`（读到的 registry 里该章不存在）＝这份镜像文件漂移。
- **修复**：`app/registry/task_registry.py` 的 `_REPO_ROOT` 用 3 级 `.parent`（registry→app→<repo>）。
  已由 `tests/unit/test_paths_anchor.py` 钉住，防止回归。

### 3.2 BLOCKED 章被“同章衍生”复读（task_id 迁移/重建丢 BLOCKED）
- **定位**：`DIAG E6.2 … ppp_after_e62=DISCOVERED`（head 不是该章也要整 registry reconcile）。
- **修复**：`reconcile_registry` 迁移分支保留 BLOCKED+consecutive_failures（`8fcbbe2`）；
  `reconcile_queue` 按 chapter 级整章冻结（`980da74`）；选下一个候选的 `_drop_frozen_candidates` 最后拦截（`78feb4a`）。

### 3.3 目录拉取为 / PROBE_EMPTY
- 症状：日志 `PROBE_EMPTY — 目录探测空(含重试)`，decision NOOP。
- 处理：常为 Xvfb / 网络抖动，直接重触一次 scheduler；连续两三次空再查登录（`login_ok`）。
- 登录失败：check `secrets.CX_USER/CX_PASS`、`checks.login_ok`。

### 3.4 定时 run 没出现
- 记住 GitHub schedule 异步：push 后可能延迟十几分钟甚至更久才激活，且 `schedule` 事件不可手动触发。
- **修 precise**：本地/远程 `gh workflow run`（`gh` CLI 配好 TOKEN）。

### 3.5 concurrency 排队
- `run.yml` concurrency 组 `xuexitong-active-course`（不抢占）。时长 ~10-17 分钟/批。若前一 run 未结束，新 run 排队等待，不是卡死。

## 4. 测试体系（防回归，每次改动跑）
```bash
python -m pytest tests/ -q            # 全量 199+ 项，覆盖 reconcile/冻结/TASKS_DIR/调度 等
python -m pytest tests/unit/test_paths_anchor.py -q          # TASKS_DIR 锚定护栏
python -m pytest tests/unit/test_reconcile_blocked_preserved.py -q  # BLOCKED 冻结

```
CI：`.github/workflows/test.yml`（coverage 跑全量），每个 commit 都跑。**改动后不要只看单测，跑全量。**

## 5. 日志/凭证
- 敏感内容（enc/t/uid/cdn/ak/cookie/token）日志中已脱敏；`state/cookies.json` 与 `.cache` 不入库、不下传。
- 运行时代码只在 GHA headed（Xvfb :94/99），本地测试用 `tests/fixtures`，不碰线上登录态。

## 6. 今天（明天）出问题的 5 步定位法
1. `gh run list` 看结论：PASS / FAIL / NOOP / queued？
2. 抓 `[scheduler] DIAG/next_task` 行 → 那章在下结论（是哪章、状态对不对）。
3. 看 `result.json` 的 `chapters_attempted / failed / timed_out / checks / runtime_result`。
4. 对表第 3 节定位 failure mode → 按其“修复”行动。
5. 改完：全量 `pytest` + CI 绿 → 手动触发一次验证。
